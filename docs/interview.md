# Interview explanation path

Use the fixture and runner as the walkthrough. These questions are tied to checked-in behavior rather than production guarantees.

1. **What does a timeout receipt prove, and what does it not prove?** Run the `timeout` case from `src/mcp_breakbench/demo.py`. Explain why the runner records `CALL_TIMEOUT`, then runs `timeout-recovery` on the same session and records one connection with zero restarts. Classifying a request as timed out is an observation about that call. It does not establish that retrying an arbitrary tool is safe: the runner has no idempotency proof or side-effect ledger. Ask what evidence a real caller would need before retrying a mutating tool.
2. **Where is authorization decided?** Trace `runner.py` from the case loop to `if case.tool not in spec.allow_tools`. Explain why a discovered tool, its description, and `readOnlyHint=true` do not authorize a call. A call needs both an explicit case entry and membership in the configured `allow_tools` set; `annotation-is-not-authorization` and `trap-was-not-called` demonstrate this boundary.
3. **What is the process trust boundary?** Inspect `client.py` and the `StdioServerParameters` construction. The configured command and argument array are trusted operator input and run with the current user's permissions. Explain why passing arguments directly avoids shell interpretation but is not a process sandbox, and why this lab cannot certify an untrusted server as safe.
4. **Why reject remote schema references before a call?** Follow `schemas.py`: local fragment references are allowed, while `$ref`, `$dynamicRef`, and `$recursiveRef` values with non-local targets are rejected before `ClientSession.call_tool`. Use the fixture's local-reference and remote-reference cases to show that the latter is rejected without executing the server-side counter. Ask what changes if a schema resolver is allowed to fetch remote content.
5. **How are failure classes kept distinct?** Map fixture cases to receipts: invalid arguments become `INPUT_VALIDATION_FAILED`, a server result with `isError=true` becomes `TOOL_RESULT_ERROR`, transport loss is a system error, and malformed structured output becomes `SDK_OUTPUT_SCHEMA_REJECTED`. Explain why these classifications lead to different investigation and retry decisions.
6. **What remains outside the contract?** Point to `implementation-notes.md`: JSON Schema does not establish business semantics, idempotency, or safety; redaction can miss encoded or unusual secrets; and finite sequential cases do not establish load behavior or production safety.
